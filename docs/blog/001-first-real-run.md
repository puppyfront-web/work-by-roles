# 我用自己开源的 AI 专家团写推广文案，被它自己的评审团拒稿了

上周末我干了一件有点绕的事：给自己的开源项目写推广文案时，没有直接动笔，而是先搭了一条 AI 流水线——三个 AI 写手按不同角度竞稿，一个 AI 主编从三稿里选定终稿；然后把终稿喂给另一组 AI 专家做发布前评审。

结果是：**终审 passed=False，拒发**。

而且它抓出的问题，一条比一条让我没法反驳：

1. 文案里写"一行 pip 就能装"——评审专家指出：**这个包还没发布到 PyPI，这是虚假陈述**。（属实，我确实还没发）
2. "评论区扣『治理』，我把踩坑文档发你"——判定为**诱导互动 + 关键词私域引流**，小红书真实红线。
3. "GitHub 搜 xxx，求个 star"——判定为**站外导流，高风险**，建议删除。
4. 最绝的是它还发现：文案一边说"改不翻车"，一边举的例子是"改一行 prompt 全崩"——**自相矛盾**，我自己写的稿自己都没看出来。

终审三维评分：事实准确性 0.35，合规安全性 0.40，转化力 0.72。附了一份逐条必改清单。

这条流水线不是我专门为了写段子搭的。它的本意是给我的日常工作用：我平时要运营好几个项目，内容产出是大头，与其每次对着空白文档，不如让三个不同风格的写手先竞稿、主编合成一版、发布前再过一遍事实和合规评审。省时间是一方面，更重要的是——**AI 编的故事，得有一个不放水的编辑盯着**。

这就要说到我把这条流水线跑起来所用的库了。

## 先说为什么会有这个库

我平时折腾多 Agent 协作，撞到过三堵墙，可能你也撞过：

1. **输出不可控**。产品经理 AI 越权改代码，两个 Agent 各说各话，输出格式每次都不一样。
2. **结论不可查**。AI 说得头头是道，但你问它"依据是什么、谁复核过、用的哪版提示词"，答不上来。
3. **变更不敢做**。改一行提示词像拆盲盒——你不知道会不会把别的能力弄坏。没有回归测试的提示词工程，和没有版本管理的代码一样危险。

市面上的框架解决"怎么把 Agent 跑起来"（LangGraph、AutoGen、CrewAI），评测工具解决"prompt 效果怎么样"（promptfoo、LangSmith）。但"跑起来之后怎么管住"这一层，一直是个空档。

所以我写了 **work-by-roles**：一个 LLM 专家团治理系统。核心思路一句话：**像管理代码一样管理你的 AI 角色**。

- **角色有契约**：每个 AI 角色一份声明式 YAML"岗位说明书"——职责 SOP、禁区、输出 JSON Schema、必须带证据引用、工具白名单、Token 配额。版本化 + 内容哈希定版，改一行都有 Diff。
- **运行有强制**：不是靠 prompt 祈祷。输出不合 Schema 直接打回；禁区命中自动记违规；工具白名单默认拒绝；证据引用不够不算合格结论。
- **协作走会审**：协调者拆解任务 → 多专家并行 → 复核人独立裁决（忽略专家自报的自信度）。**分歧留存不仲裁**——谁对谁错，留给你判断。
- **变更有回归**：黄金用例 + 基线快照 + 一键回归。改契约、换模型之后，能力退化自动检出。
- **全程可审计**：每次编译/调用/校验/裁决都产生 TraceID 关联的审计事件，可导出审计包。

## 这套机制不是纸面设计——上面那个拒稿故事里，它救了我三次

流水线第一次接真实模型（DeepSeek），连续暴露了三个引擎层的 bug。有意思的是，**每一次都是治理机制自己先把问题拦下来的**：

- 第一次：三个写手全部通过 Schema 校验，但主编阶段崩了——真实模型返回的评分是嵌套结构（`{"维度": {"score": 0.8, "评语": …}}`），引擎按平铺数字解析直接崩。修复后加了容错转换。
- 第二次：一个写手被"禁区"误杀。禁区规则会编译进 system prompt，写手在自检时复述了规则原文（"本文未编造数据…"），字面匹配把它判成了违规。修复为否定感知匹配。
- 第三次最有意思：机制全绿，但主编裁决"三稿均不可用"——一个写手跑题写了职场感悟，两个直接回复"请提供选题"。根因是编排缺陷：**专家只收到了协调者的子指令，没收到原始需求**。真实模型的子指令是"写故事型初稿"这种薄指令，不像测试里那样自包含。修复：专家输入 = 原始问题 + 子任务。

第四次跑，全绿，产出就是开头那篇被拒的稿子。三次失败全部有审计事件留痕——**失败的原因比成功更重要，而大多数 Agent 框架在失败时只给你一个 stack trace**。

这些修复连同完整过程记录都在仓库里（`docs/REAL_WORLD_VALIDATION.md` §7），包括每一次的原始输出。

## 30 秒上手（不需要任何 API Key）

```bash
pip install "work-by-roles[server]"
wbr list-teams
wbr run-team content_creation_team "为你的产品写一篇小红书笔记"
```

默认走内置演示 Invoker（确定性输出、零外部调用），先看清会审流程长什么样。

接真实模型只要三个环境变量，OpenAI / DeepSeek / Kimi / Qwen / GLM / Ollama / vLLM 等任何 OpenAI 兼容端点通用：

```bash
export WBR_LLM_API_KEY=sk-...
export WBR_LLM_MODEL=deepseek-chat
export WBR_LLM_BASE_URL=https://api.deepseek.com/v1
wbr run-team content_creation_team "为你的产品写一篇小红书笔记" --live
```

还有可视化画布：`uvicorn --factory wbr.app.api.main:create_app --port 8000`，浏览器打开 `/canvas`，拖拽搭自己的专家团、导入官方模板、跑会审、看分歧、导审计包。

目前自带四个官方模板：架构评审团、安全审计团、内容创作团（竞稿）、内容评审团（把关）。自定义一个专家也就是写一份 YAML 的事。

## 定位与诚实声明

- 和 LangGraph / AutoGen / CrewAI **不竞争**：它们管编排，这个库管治理。存量 LangGraph 项目可以用 `WBRGuard` 三行接入。
- 和 promptfoo / LangSmith **互补**：它们测效果，这个库在运行时强制边界 + 契约版本闭环。
- 现状：391 个测试全绿，CI 跑 Python 3.10 / 3.13 双版本，MIT 协议。
- 诚实的部分（评审团队友教我的）：**这个包还没发布到 PyPI**，目前请从源码安装（`pip install -e .`）；多阶段流水线（专家间串行依赖）在 roadmap 上，当前生产型团队的范式是"并行竞稿 + 主编合成"。
